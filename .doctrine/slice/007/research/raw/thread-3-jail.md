## Thread 3 — classify from the jail

### Facts

1. The jail is `jailLib.makeJailedAgent` from the agents lib, instantiated as `mkJailedMalebolge` with `name = "malebolge"`, `agent = malebolgeDaemon` (node running `src/daemon-main.ts`), `profile = "offline"`, `mountLaunchDir = false`, `persistedHome = "malebolge"`, `workspaceDeps = []` (`.doctrine/state/slice/007/satan-flake.nix:321-335`, `:232-234`).
2. What it can read is enumerated in `malebolgeRoomJailOptions`: ro `malebolgeRoot`, `/run/capsule-room`, `roomStateDir`, the room ssh key, the door file, the rendered ssh_config, `/run/user/1000/satan/mcp`, `/home/david/satan-corpus`, the gateway key file and catalog (`satan-flake.nix:281-294`); rw only `malebolgeRuntimeDir`, `malebolgeStateDir` (`:297-299`) plus the screwtape store (`:318`).
3. `HOME` is the jail's own persisted home, `~/.local/share/jail.nix/home/malebolge` (`satan-flake.nix:334`, probe `:485`), not `/home/david`; so neither `~/.config/credstore.encrypted` nor `~/.nix-profile` exists inside.
4. There is no network: the offline profile plus `--unshare-net` in the launcher probe (`satan-flake.nix:325`, `:489`). Jev's `base_url` (`screwtape-module.nix:68-73`) — HTTPS or the loopback relay — is therefore unreachable from the jail by any key route.
5. `XDG_RUNTIME_DIR` is forwarded (`satan-flake.nix:269`) but only `/run/user/1000/satan/mcp` and `/run/user/1000/satan/durable/room` are bound (`:287`, `:290`), so the user bus (`/run/user/1000/bus`) and the manager's private socket are absent; the jail scan explicitly forbids the wholesale `--bind /run/user/1000 /run/user/1000` (`:595-603`).
6. The daemon gets the raw binary, by store path, plus its config: `(set-env "MALEBOLGE_SCREWTAPE" "${package}/bin/screwtape")`, `MALEBOLGE_SCREWTAPE_CONFIG`, `bind-pkg` for both, `readwrite storeDir` (`satan-flake.nix:306-319`); the package/config/store come from the deployment's `services.screwtape` (`:316-320`, `:417-418` uses a probe stand-in).
7. The HM wrapper is *not* in that closure: it is `home.packages = [wrapper provision]` (`screwtape-module.nix:369`), i.e. `~/.nix-profile/bin/screwtape`, which the jail's `$HOME` shadows.
8. Malebolge's own contract bakes this in: `MALEBOLGE_SCREWTAPE` is documented as "the screwtape executable itself (not a wrapper that adds `--config`)" (`src/config.ts:42-44`), read only for profiles whose toolset allows `mail` (`src/config.ts:99-107`), and the adapter spawns `[binary, "--config", config, verb…]` with `env: { HOME }` and `inheritEnv: false` (`src/mail/screwtape.ts:250-253`; `docs/internals.md:143-150`) — no `XDG_RUNTIME_DIR`, no `DBUS_SESSION_BUS_ADDRESS`, no `PATH`, 10 s timeout.
9. The wrapper exists only when `services.screwtape.jev != null`, and reroutes `classify` (but never `classify --state`) into `systemd-run --user --pipe --quiet --wait --collect -p LoadCredentialEncrypted=jev:<configHome>/credstore.encrypted/screwtape.jev -p LimitCORE=0 -E ERL_CRASH_DUMP_SECONDS=0 <screwtape --config …> "$@"` (`screwtape-module.nix:79-101`; README `:372-390`). Only the credential's path is in argv.
10. Outside the wrapper `classify` reads the key from `$CREDENTIALS_DIRECTORY`, and the README states "there is no other way in" (`screwtape-readme.md:389-391`); a missing credential is the `no_jev` failure, exit 2 (`.doctrine/slice/007/slice-007.md:42-46`).
11. The encrypted credential is `~/.config/credstore.encrypted/screwtape.jev`, written by `screwtape-provision jev` via `systemd-creds encrypt --user --name=jev` under `umask 077` (`screwtape-module.nix:12,17-20,105-160`; `screwtape-readme.md:560-575`); the decryptor is the *user manager*, at unit start (`screwtape-module.nix:379` for sync; `:81` for the transient unit).
12. Binding that directory is already a declared launch error: `~/.config/credstore.encrypted`, `~/.config/systemd/user`, the store dir and their ancestors including `$HOME` must not be bound (`screwtape-readme.md:610-618`).
13. ASM-001 is "held" exactly on this premise: mail runs as the operator on the host, screwtape runs with `--config` and a child env of `HOME` alone, reading its store read-only (`.doctrine/knowledge/assumption/001/record-001.toml`, `record-001.md:1`); slice OQ-3 flags reaching the user manager as "the slice's riskiest unknown" (`.doctrine/slice/007/slice-007.md:89-91`, `governance.md:86-91`).

### Options

**(a) Call the wrapper / `systemd-run --user` from inside the jail.** Requires satan to bind the user bus (or `$XDG_RUNTIME_DIR/systemd/private`), the credstore file, and the HM profile's wrapper, and malebolge to stop forcing `env: { HOME }`/allow a longer timeout. Repos: satan (binds, probes `jailProbes.malebolge` `satan-flake.nix:459-512`), malebolge (invocation, 10 s bound), screwtape (nothing). Trade-off: the jail gains control of the operator's user manager (start/stop/attach any unit, portals, ssh-agent) *and* the encrypted key, which same-uid `systemd-creds --user --decrypt` can open — both directly contradict `screwtape-readme.md:610-618` and the runner-socket scan (`:595-603`), and it still cannot work for the Jev round trip under `--unshare-net`.

**(b) A separate classify path handed in by satan's flake.** A second variable (e.g. `MALEBOLGE_SCREWTAPE_CLASSIFY`) and a `ScrewtapePaths` field (`src/config.ts:41-50`, `src/mail/screwtape.ts:250-253`), plus a satan `set-env`/`bind-pkg`/probe. Only meaningful if that path is *not* the decrypting wrapper: pointing it at the HM wrapper is option (a) with extra wiring and the same exposure; pointing it at a passthrough gains nothing.

**(c) Host-side classify broker over a bound unix socket** (the shape the gateway already uses: `readonly "/run/llm-gateway-client"` `satan-flake.nix:280`, `:479`). Screwtape's module adds a socket-activated unit whose own `ExecStart` runs `screwtape --config … classify` with `LoadCredentialEncrypted=jev:…` — the pattern of `:375-381` — so the key is decrypted only in that unit; satan binds the socket ro and sets an env var; malebolge points its mail adapter (or a new classify port call) at the socket instead of spawning the binary, keeping `env: { HOME }`. Trade-off: the key never enters the jail, the jail gains only a classify oracle over bounded stdin, and the jail stays offline while the broker does the HTTPS hop. Cost: a new long-running surface, per-call cost still one unit + one Jev call (OQ-4, `slice-007.md:93`).

**(d) Put the key in the jail** (plaintext via env/file, or bind credstore + `systemd-creds`): rejected — key disclosure to agents, forbidden by DEC-038/DEC-016 posture, and still useless without network.

Note: `classify --state` needs neither key nor network and would work today through the raw binary (`screwtape-module.nix:84`, README `:376-378`); only the Jev call is blocked.

### Unknowns

- How the agents lib actually renders the `offline` profile (user namespace, further `--unshare-*`, seccomp/landlock) and whether `XDG_RUNTIME_DIR` resolves to an existing path inside; only bwrap probe strings were visible.
- Whether `try-fwd-env "XDG_RUNTIME_DIR"` forwards the host's `/run/user/1000` or the daemon's own runtime dir, and hence what `$XDG_RUNTIME_DIR/bus` would name.
- Whether `systemd-run --user` would even succeed from a plain `{ HOME }` environment (no `XDG_RUNTIME_DIR`), and what `classify` exits with when `$CREDENTIALS_DIRECTORY` is unset (the `no_jev`/exit-2 mapping is asserted in the slice, not in the staged README).
- Exact semantics of user-scope credential decryption by a same-uid process — the "same uid ⇒ can decrypt given the ciphertext" claim above is inference from DEC-016's uid model, not a staged statement.
- Whether a host-side broker socket is acceptable under the mail-security posture (DEC-038, RSK-002), and whether satan's runner-socket/`op`-unjailed scans would permit a new socket bind.
- Whether Jev access is expected via `api.typesafe.ai` or the local relay (`screwtape-module.nix:69`), which decides broker networking.
