## Thread 1 — governance applicability

### Binding constraints

| id | rule (one sentence) | bearing on SL-010 |
|---|---|---|
| DEC-016 | A `topic` first-line frame writes one topic record and replies `topics:[{name,cwd?}]`; `list` gained `topic`/`topics` keys; first-line frames dispatch through one table (amended 2026-10-24 after SL-003). | Scope 1, 4, 6: `model` is a third frame key and `TopicSummary` a third field; the reply shape is fixed here, so no new reply type for topic writes. |
| DEC-007 | A `list` reply is a framed object; new **keys** widen additively, a new **element type** does not; older daemons refuse new keys as `<frame>: unknown key …` → restart hint (amended for `topic`/`topics`). | Scope 1 and 6: `TopicMessage.model`, `TopicSummary.model` and a per-element `topic` on `list` are all key widenings — permitted; changing the element type is not. |
| DEC-017 | `--topic NAME` attaches to the topic's latest (with `--new`/`--cwd`); `--set-topic NAME [--dir|--no-dir]` creates or re-points a topic; `--topics` stands alone; one `checkAlone` enforces exclusivity. | Scope 4: `--model REF`/`--no-model` must ride `--set-topic`, be exclusive with attach/list flags, and pass `checkAlone` exactly as `--dir`/`--toolset` do. |
| DEC-008 | `--list` prints ids one per line; invocations are a tagged union with `UsageError` refusals; the skew predicate (`skewOf`) covers `unknown message type` and strict-key refusals; `request` resolves a typed reply and prints nothing. | Scope 4/6: a new key means a new skew shape (`attach: unknown key model`) and the new command should reuse `request`, not a second writer. |
| DEC-025 | A conversation's toolset is fixed at creation and never changes; forks inherit it; a daemon topic may carry a toolset, written through the topic frame and `--set-topic`, **checked against the profile's allowed toolsets**; a new conversation's toolset is its topic's, else the profile default; changing a topic affects only later conversations. | The whole slice is this decision applied to a second field: scope 1–5, plus OQ-1 and OQ-2. The topic-write validation rule is the direct precedent for "a set model must be in the gateway catalog". |
| DEC-024 | Every create path passes one `init` naming a toolset; startup backfills stored conversations lacking one and refuses to start if any still lacks one. | Scope 3: the same single `init` (`toolsetInit`) is where "the topic's model, else the daemon default" belongs — it already reads the topic inside the creating commit. |
| DEC-029 | A toolset is a conversation's complete ordered extension list; the entry stores the **name**; contents are re-derived per profile at startup. | Analogue and limit: a stored *model reference* is like the name (re-validated), not like the frozen list — relevant to OQ-1. |
| DEC-012 | The `conversationCreated` hook writes the index entry in the creating commit: a fork takes its parent's topic and records `parent`; anything else joins `default`; a caller-named topic comes via a later `init`. | Scope 3 and OQ-3: where a fork's topic (and so a topic's model, if it followed the topic) is decided; the model itself is copied with the agent document. |
| DEC-033 | A fork's index entry copies its parent's toolset in the creating commit; startup refuses a fork whose entry has none rather than defaulting it. | OQ-3: the "fork keeps its parent's" rule. A fork already copies the parent's stored agent settings, so the model inherits with no write — the decision's shape should be cited, not re-invented. |
| DEC-034 | `thread_start {intent, context?, topic?}` starts in the topic (default: the caller's), refusing unknown topics; **toolset is the topic's, else the profile default; cwd is the topic's, else the daemon default**. | OQ-3: a started thread's model is currently the daemon default (SL-006 design: `defaults: ConversationDefaults; /** Model and cwd a started thread takes; cwd yields to its topic's. */`), so "follows its topic" is a change, not an application. |
| DEC-015 | A topic's latest is its highest id; `default` always exists implicitly, cannot be created or given a directory, and **the topic frame refuses `default`**. | OQ-2: a model on `default` is not reachable through the existing write path, and DEC-015's rationale (a default-topic directory would never reach root or legacy `new`, so D1 holds halfway) is the exact argument about scope 3's "otherwise the daemon default". |
| DEC-037 | Latest skips tool-created conversations (`parent`/`startedBy`). | OQ-3 boundary: a topic-model change must not make `attach --topic` land in a thread. |
| DEC-013 | The index is one session-scoped document: `{topics:{name:{cwd?}}, conversations:{id:{topic,parent?}}}`; topic listing reads it, not `scanConversations`. | Scope 1: `TopicRecord` and `TopicSummary` read one document — the model lives beside `cwd`, and the `list` key must be filled from this document, not a scan. |
| DEC-014 | `--here` is host-profile only and exact-match, never picking among matches; the `topics` reply carries the daemon's profile. | Scope 5/6: the client learns the answering daemon's profile from `--topics`; any new topic-model command using that listing inherits the same rule. |
| DEC-009 | `C-u M-x malebolge-attach` prompts over daemon ids via a synchronous `--list` subprocess, `new` appends a candidate, the target becomes argv, the switch is refused with a non-empty draft, bounded by `--list-timeout`. | Scope 5/6: "choosing `new` asks for a topic" and "show each conversation's topic" are extensions of this one prompt path and its argv shaping (`--topic NAME --new`). |
| DEC-010 | Bare ids suffice; the human path never requires typing one; label derivation, fuzzy matching and paging stay refused (as amended: `--here` host-only). | OQ-5: showing a model on the chooser line brushes against "no label derivation"; DEC-039's `--list` marks (`fork of 12`) are the accepted precedent for extra per-line facts. |
| DEC-006 | Output following uses comint's native point-at-mark follow; no custom hooks. | Scope 6 only insofar as the chooser must not disturb transcript following (a prompt, not a new render path). |
| DEC-032 | Talk sets are a per-profile map beside `PROFILE_TOOLSETS`; `toolset` keeps its name; the rename is backlog work. | Scope 4/5 naming: new flags and records should say `model`, and the toolset rename (CHR-004) is sequenced, not merged. |

### Checked, not applicable

- **DEC-023** — `superseded` by DEC-029; cite DEC-029.
- **DEC-011** — pi 1.4.0 landing order, already done; no design constraint.
- **DEC-018, DEC-019, DEC-020, DEC-021, DEC-022** — prompt/env plumbing for conversation context; SL-010 explicitly does not put the model in the prompt or env.
- **DEC-026–DEC-063 (mail, classify, bookmarks, untrusted text)** — a topic's model changes which model runs, not what tools or text reach it; no rule here.
- **DEC-031, DEC-035, DEC-036, DEC-040–DEC-046** — fork point, post delivery, caps/reaping, conduct prose; unrelated to model selection.
- **DEC-038, DEC-041** — threads are room-only and sequential; they bound who may start threads, not what model a thread runs.
- **DEC-039** — cited above only for its `--list` marking precedent; its journal/notify obligations do not bind SL-010.
- **DEC-064–DEC-076 (bridge)** — bridge mode membership and pairing; a topic model does not touch them. Note DEC-071's consequence that a new mode must be allowed before stored — not triggered here.
- **DEC-093 (~/flakes)** — external, tier 5 here: it establishes that `openai-dav/*` and `openai-david/*` are in the catalog the daemon reads; it is context for scope 2's check, not an authority over malebolge's design.
- **RFC-001, RFC-003** — no model-selection rule; RFC-003's mode/talk-set model is DEC-032's business.
- **IMP-017** — the fork toolset mechanism it designed shipped as DEC-033; nothing left to pull.
- **CHR-004** — sequenced with this slice per the slice's Follow-Ups; no constraint beyond naming discipline.

### Revision candidates

- **RFC-002 D3** ("A topic carries only `cwd`. No model or extension defaults yet") — SL-010 is the case D3 anticipated ("the creation-time rule makes them cheap to add"); the model half becomes false. Already de-facto amended for toolset by DEC-025; RFC is tier 5, so treat as evidence to update, not a gate.
- **DEC-025** — extended: a topic now carries `cwd`, `toolset` and `model`, and its validation clause ("checked against the profile's allowed toolsets") is generalised to a second authority (the gateway catalog). Extend as `model` alongside, or account for DEC-025(2)'s immutability and its "affects only conversations created afterwards" verbatim.
- **DEC-016** — extended: `TopicMessage`/`TopicSummary` gain `model`; no reply type changes. Record as amendment, keeping DEC-007's key-vs-element line explicit.
- **DEC-017** — extended: `--model`/`--no-model` join the `--set-topic` family in `checkAlone`; the exclusivity table and usage text change.
- **DEC-012 / DEC-033 / DEC-034** — OQ-3 potentially amends these: DEC-034 (and SL-006 design's `defaults: ConversationDefaults` seam) gives a *started* thread the daemon default model, so "a started thread follows its topic" is a real amendment; a fork's inheritance needs no amendment (the agent document carries the model), but should be recorded as the reason DEC-033 needs no change.
- **DEC-015** — if OQ-2 answers yes, the `default` topic's "cannot be given a directory / the frame refuses `default`" needs refining for `model`, with reason.
- **DEC-010** — OQ-5 may extend "bare ids suffice" with a per-line model, following DEC-039's marks.

### Open-question inputs

- **OQ-1 (stored model the catalog dropped)** — DEC-025(2) + SL-005 design's reconcile step ("A topic record or an entry whose toolset the profile does not allow refuses startup, naming it … Silently widening a mail topic to `interactive` is worse"), DEC-024(3) (refuse-or-refuse-startup over defaulting), DEC-033 (refuse rather than silently default), DEC-055/DEC-049 (refuse each use, naming the reason), DEC-014 (refuse, never pick one). Supports the proposed explicit refusal over silent fallback.
- **OQ-2 (`default` carries a model)** — DEC-015 (reserved, not creatable, frame refuses `default`; rationale about root and legacy `new`), DEC-025 (root and legacy `attach new` both take the profile default), DEC-024 (root's selection is written by the reconcile, not by a topic). Governance currently forbids it by construction; changing that is a DEC-015 revision.
- **OQ-3 (threads and forks)** — DEC-034 (thread_start: topic's toolset/cwd, daemon-default model), DEC-033 (fork copies the parent's toolset in the creating commit), DEC-012 (fork takes the parent's topic; `init` sets a named topic), DEC-031/DEC-037 (fork point, latest skips threads), DEC-038 (threads room-only). Note the mismatch: the toolset precedent is *split* (fork=parent, start=topic), and today's start model is the daemon default.
- **OQ-4 (model completion in Emacs)** — DEC-016 (first-line frames dispatch by one table; a new listing is a new reply type, which DEC-007's amendment shows is permissible), DEC-007 (key widening vs element type), DEC-008 (`skewOf` must learn the new refusal; a new frame on an old daemon prints the restart hint), DEC-009 (synchronous subprocess, `user-error` on a non-zero exit, never silently fall back). No decision names a model-list; unverified whether anything else does.
- **OQ-5 (chooser line: topic only, or topic and model)** — DEC-007/DEC-016 (a per-element `topic` key is additive; per-element model too, if the daemon fills it), DEC-039 (`--list` lines already carry marks such as `fork of 12`), DEC-010 (label derivation refused; DEC-039 is the accepted narrow exception), DEC-009 (the chooser's candidates come from the listing's text), DEC-008 (`render.ts`/`Printable` is the one place that text is made).
