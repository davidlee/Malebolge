## Facts

1. **`bridge` as a toolset.** Declared in the closed union `Toolset = "interactive" | "mail" | "bridge" | "job"` (`src/toolsets.ts:9`); catalogue entry `bridge:` is interactive's list minus `threads`, with `bridge` before `SATAN` (`src/toolsets.ts:39-49`); room-only allowance `room: { default: "interactive", allowed: ["interactive","mail","bridge"] }` (`:80-82`); talk-set map gives `bridge` none (`:89-92`), so `requireSameTalkSet` refuses it as caller or target (`:99-118`). Other places naming the string as a toolset: `src/bridge/listener.ts:239` (require hook), `:279` (topic write), `src/persona.ts:25-33` (persona files), `test/toolsets.test.ts:42,285-305,390-397`, `test/persona.test.ts:102-117`, `test/bridge-pairing.test.ts:312,338`, `test/wake-tools.test.ts:781`. `src/daemon-extensions.ts:48` names the *extension* `bridge`, installed from `allowedNames` (`:71-76`), not a toolset.

2. **Pair's creation path.** pi sends `pair` after `state.ts` builds `{ type:"pair", posture, project: state.project }` (`pi-bridge/state.ts:673-676`; also the re-pair after end, `:394`). Listener: first line parsed (`src/bridge/listener.ts:444-450`) → `BRIDGE_FIRST_LINE.pair = pairRow` (`:409-413`) → `pairRow` mints a token before any commit (`:292`), validates the topic name as `` `${frame.project}-bridge` `` (`:295`), then `createBridged` (`:270-283`): `readIndex`, `isKnownTopic`, `conversations.setTopic({name, toolset:"bridge"})` if absent (`:277-280`), `topicCwd` (`:281`), `create(...)` (`:282`). `create` is `harness.createConversation` with an ownerless conversation and the init (`src/conversations.ts:240-250`); the init is `bridgedInit` → `topicInit(..., { require: requireBridge(name) })` (`src/bridge/listener.ts:249-263`), which inside the creating commit chooses `record?.toolset ?? policy.default`, `requireAllowed`, then `hooks.require?.(chosen)` (`src/conversations.ts:206-226`), configures the extension list (`:227-231`), and `openPairing` writes the pairing (`src/bridge/listener.ts:261`). `requireBridge` refuses any toolset but `bridge` (`:236-242`). Then `bindAndFollow` (`:301`, `:170-193`).

3. **The pairing document.** `defineDoc` with `scope: "conversation"`, `fork: "initial"`, `history: "latest"`, initial `tokenHash: ""` = not bridged (`src/bridge/pairing.ts:56-73`); keyed by `ConversationId` (`:74-76`); one document per conversation, so a conversation structurally holds at most one pairing (one `tokenHash`, one outbox, `:30-46`). A new `pair` today does **not** touch an existing conversation — it creates a second conversation in the same topic (`test/bridge-pairing.test.ts:358-373`). `openPairing` resets everything (`:115-129`), so re-pairing an existing id is a plain overwrite. Resume: `resumeRow` → `checkPairing` (snapshot read, nothing written, `src/bridge/listener.ts:216-225`) → `checkToken` not-bridged/bad-token/ended ordering (`src/bridge/pairing.ts:138-154`) → `bindAndFollow`. Supersede is per connection, not per doc: `bind` closes the previous connection with `refused("superseded by a newer connection")` (`src/bridge/listener.ts:146-154`); `unbind` on close (`:157-163`). End commits `ended` and closes (`:383-388`, `src/bridge/pairing.ts:197`); the doc keeps `tokenHash` and outbox, and `boundLine` refuses every non-`end` frame on an ended pairing (`:469-474`). An ended pairing can only be revived by `openPairing` (a new pair).

4. **SATAN side.** `bridge_post` is registered unconditionally with the extension (`src/bridge/extension.ts:53-86`); there is no availability gate — unpaired/ended availability is decided at execute time by `appendOutbox` (`src/bridge/pairing.ts:154-160`) and returned as a `refusal` (`src/bridge/extension.ts:74-82`). The prompt section is **dynamic per render**: the section body is a function that reads `pairingSnapshot(read, conversationId)` each time it is evaluated (`:87-96`), and `bridgeSectionText` renders `BRIDGE_UNTRUSTED` alone when the doc is undefined or unbridged (`:41-45`), otherwise untrusted + environment + posture (`:45`). So today the section always renders something; SL-011 makes the unpaired case render nothing. Bookmarks is the precedent for "installed, refusing when unconfigured": the source rejects with `BookmarkSourceError("not_configured", "bookmarks are not configured")` (`src/bookmarks/backup.ts:278-283`), while the extension itself is static (tools + fixed tagged section, `src/bookmarks/extension.ts:15-21`).

5. **Startup reconcile.** `reconcileToolsets` runs in one commit (`src/session.ts:153-190`); `allowedToolsets` calls `requireAllowed` on every stored topic toolset and every entry toolset, naming the subject (`:131-147`), and `entryToolsets` backfills a missing toolset with the profile default but does **not** remap an existing one (`src/topics.ts:327-348`). If `bridge` is removed from `CATALOG`/`allowed`, a store holding a `bridge` topic or conversation makes the daemon **fail to start** with `topic <name>: toolset bridge is not allowed on profile room` or `conversation N: toolset bridge is not allowed on profile room` — pinned analogously by `test/session.test.ts:458-481`. (If the name stays in the union but leaves `CATALOG`, `toolsetList` returns `undefined` and the `Record<Toolset,…>` type fails to compile: `src/toolsets.ts:24,64-68`.) A migration (rewrite to `interactive`) is the only non-refusing path; no such code exists.

6. **Attach tracking.** The daemon tracks bindings only per connection object: `Connection.bound` (`src/daemon.ts:57-60`), set in `bind` (`:140`), created per socket in `startConnection` (`:343-362`); there is no store-wide map and `serve()` holds no set (`:369-373`). The bridge listener has its own `bindings: Map<ConversationId, Connection>` (`src/bridge/listener.ts:86-96`, `:549`) — bridge connections only. `BridgeHost` carries session, conversations, defaults, profile, catalog, satan, log, now (`src/daemon-start.ts:283-300`) — no attach state. Both listeners live in one process and are wired in one function (`:383-410`), and a cross-listener hook already exists (`onOperatorInput`, `:272-279`, `:334-338`), so exposing "attached conversations" is a small shared-object addition rather than a process boundary. Nothing in `pi-bridge/` or Emacs reports its attachment to the bridge either.

7. **`threads` + `bridge` coexistence.** Talk sets are the only gate: `bridge` has no talk set (`src/toolsets.ts:89-92`), so a bridge conversation can only self-wake (`src/wake/tools.ts:137-143` with `reachRefusal` `:71-93`), an interactive conversation cannot wake into a bridge topic, and thread start/post refuse a bridge target via `requireSameTalkSet` (`src/threads/admission.ts:36-46`; tool description `src/threads/tools.ts:514`). Folding bridge into `interactive` removes that isolation: a bridged conversation becomes wakeable/thread-postable exactly like any other interactive conversation, and gains `tasks`+`threads` (the `bridge` catalogue deliberately omits `threads`, `src/toolsets.ts:25-38` vs `:39-49`). Pins: `test/wake-tools.test.ts:778-818`, `test/toolsets.test.ts:390-397`.

8. **pi-bridge command side.** `/bridge` parsing: `bridgeCommand` splits on whitespace, accepts `end` alone or `pair <posture>`, else notifies `BRIDGE_USAGE` (`pi-bridge/shell.ts:516-544`, usage string `:55`); `postureOf` (`:545-551`). Pair frame construction: `src`-less `{ type:"pair", posture, project: state.project }` (`pi-bridge/state.ts:673-676`, `:394`); wire spec `pair: { posture: oneOf(POSTURES), project: text }` (`pi-bridge/wire.ts:172`, frame type `:26-30`). The `malebolge-bridge` command (`pi-bridge/command.ts:1-4`) takes only `send|tee [--turn]` (`:43-55`), reads `MALEBOLGE_BRIDGE_CONVERSATION`/`_TOKEN` from env (`:182-187`; set by the spawn hook, `pi-bridge/shell.ts:47-52`, `:485-496`), and posts once (`:201-208`). Project basename is used at `pi-bridge/shell.ts:710` (`sessionStartEvent`), `pi-bridge/command.ts:190` (`ends.project`), and as the topic name in notices `` `${project}-bridge` `` (`pi-bridge/notices.ts:45-47`, `pi-bridge/shell.ts:593`).

9. **Emacs.** The conversation id appears once, as a transcript notice: `attached: (event) => p.notice("attached to conversation N" + summaryClause)` (`src/render.ts:372-376`, summary clause `:330-334`), printed through the comint attach client whose only reaction to `attached` is `state.attached = true` (`src/attach.ts:180-190`). The header line is the fixed key summary (`emacs/malebolge.el:107-110`, installed at `:192`, `:199`); there is no mode-line entry and no id in the header. So after attach the id is visible only in the transcript line (and in listing prompts, `:333-380`).
