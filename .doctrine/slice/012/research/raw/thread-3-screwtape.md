## Thread 3 — screwtape identity and mailboxes

### Cited facts

**1. Message identity.** A message's `id` is the **JMAP Email id** — `stage/screwtape/README.md:154` ("JMAP message id"), carried through as `Message.id` from JMAP `id` (`stage/screwtape/src/screwtape/normalise.gleam:24`) and stored as the primary key of the `message` table (`stage/screwtape/src/screwtape/store.gleam:734`). The RFC 5322 Message-ID is kept **separately and as a list**: `messageId` is requested as an Email property (`stage/screwtape/src/screwtape/jmap/request.gleam:28-30`), decoded as `Option(List(String))` (`stage/screwtape/src/screwtape/normalise.gleam:33`), normalised into `HeaderIds.message_id` with an absent header becoming `[]` (`stage/screwtape/src/screwtape/normalise.gleam:366-372`), stored one row per header value and position in `message_header_id` (`stage/screwtape/src/screwtape/store.gleam:762-770`), and reassembled in header order by `header_ids_of` (`stage/screwtape/src/screwtape/store/query.gleam:523-551`). `message_id` is printed as a JSON **array** and only by `read` — `list` and `thread` summaries do not carry it (`stage/screwtape/README.md:192`, `stage/screwtape/README.md:148-164`, `stage/screwtape/README.md:336-338`), and `list`/`thread` items expose only `id` (`stage/screwtape/README.md:154`). There is no `new` verb; the vocabulary is `sync`, `mailboxes`, `list`, `read [<id>|--after]`, `thread`, `classify[ --state]` (`stage/screwtape/README.md:37-46`, `stage/screwtape/src/screwtape/argv.gleam:94-123`). Headers **can** be fetched by id without bodies: `read <id> --max-bytes 0` is legal (`--max-bytes` accepts ≥ 0, `stage/screwtape/src/screwtape/argv.gleam:175-179`) and returns the whole header set plus `output_truncated` (`stage/screwtape/src/screwtape/render.gleam:162-200`). `message_id: []` is printed as an empty array, never omitted (`stage/screwtape/README.md:129`, `stage/screwtape/src/screwtape/normalise.gleam:368`).

**2. Mailboxes.** `screwtape mailboxes` takes no arguments (`stage/screwtape/src/screwtape/argv.gleam:96-97`) and prints `{"version":1,"kind":"mailboxes","data":{"items":[mailbox]}}` ordered by `sort_order`, then name, then id (`stage/screwtape/README.md:133-136`, `stage/screwtape/src/screwtape/render.gleam:116-121`). Each item is `{id, name, parent_id, role, sort_order, total_emails, unread_emails}` (`stage/screwtape/README.md:138-146`, `stage/screwtape/src/screwtape/render.gleam:261-271`). `id` is the JMAP mailbox id; `name` is "as the server spells it" (the JMAP leaf name); `parent_id` is the only hierarchy signal — screwtape never composes a path; `role` is the JMAP role, "for example `inbox`" (`stage/screwtape/README.md:140-143`). The list is the **whole account**, not the window: `Mailbox/get` is sent with `ids: null` (`stage/screwtape/src/screwtape/jmap/request.gleam:73-79`). Name matching is role-first then exact name (`stage/screwtape/src/screwtape/model.gleam:184-196`), used both for `window.mailboxes` (`stage/screwtape/src/screwtape/sync.gleam:522-534`) and for `--mailbox <id|role|name>` (id first, then role, then name — `stage/screwtape/src/screwtape/cli.gleam:226-245`). **No IMAP concept exists anywhere** in the README or `src/`: no folder separator, no IMAP path, no UID/UIDVALIDITY, no UID mapping (absence across `stage/screwtape/README.md:133-146`, `stage/screwtape/src/screwtape/request.gleam` property/method lists at `:28-30`, `:46-51`, `:73-79`).

**3. Per-message state.** Yes, both. Keywords are exposed as `keywords: [string]` on `read` (`stage/screwtape/README.md:186`) and as the derived booleans `is_seen` (`$seen`) and `is_flagged` (`$flagged`) on every summary-shaped item (`stage/screwtape/README.md:160-161`, `stage/screwtape/src/screwtape/normalise.gleam:358-362`). Mailbox membership is exposed per message as `mailbox_ids: [string]`, sorted (`stage/screwtape/README.md:162`, `stage/screwtape/src/screwtape/store/query.gleam:799-801`) — ids only, never names. Freshness: a systemd user timer refreshes the store, default `onCalendar = *:0/15` (`stage/screwtape/README.md:570`); `sync` is service-only and cannot be run from a shell (`stage/screwtape/README.md:465-473`); the timer runs only while the user manager does, with `Persistent=true` catching up at login (`stage/screwtape/README.md:585-588`); a rate limit is not retried, the next tick is the retry (`stage/screwtape/README.md:668-670`). Each run re-fetches `mailboxIds` and `keywords` for changed and window messages (`stage/screwtape/README.md:498-504`, `stage/screwtape/src/screwtape/jmap/request.gleam:28`), so state can lag by up to one timer interval (plus run time), or indefinitely if the service is disabled or failing.

**4. Mirror window — yes, a message the agent saw can become unresolvable.** The window is named mailboxes, `maxAgeDays` (default 30), `maxMessages` (default 2000), `retainMessages` (`stage/screwtape/README.md:24-29`, `stage/screwtape/README.md:561-564`). Retention keeps the newest N and, when set, ignores `maxAgeDays` (`stage/screwtape/README.md:514-518`), and it "covers the configured mailboxes only: a message moved out of every configured mailbox, for example archived, is dropped from the store" (`stage/screwtape/README.md:520-522`). Sync also drops ids the server reports destroyed (`stage/screwtape/src/screwtape/retain.gleam:25-43`, `:33`). Two further traps: `thread` items may name message ids the store does not hold, printed as `{id, in_store: false}` (`stage/screwtape/README.md:336-338`), and `thread_email` has no foreign key to `message` (`stage/screwtape/src/screwtape/store.gleam:813-820`), so those ids are unresolvable; and cursors are not scoped to an account, so after re-pointing the store a stale cursor is still accepted (`stage/screwtape/README.md:456-457`). A failed lookup is `Usage("unknown_message")`/`("unknown_thread")`, exit 2, nothing on stdout (`stage/screwtape/src/screwtape/cli.gleam:261`, `:303`, `stage/screwtape/README.md:80`, `:104-105`).

**5. Write/plan concept.** Only as stated intent, never as surface: "Intended to broker read-only agent access for summarisation & authoring reviewable, auditable execution plans for deterministic invocation by the user" (`stage/screwtape/README.md:10-11`). No verb, field or table is named plan/proposal, and no write JMAP method exists — the client's method set is `Mailbox/get`, `Email/query`, `Email/get`, `Thread/get`, `Email/changes` only (`stage/screwtape/src/screwtape/jmap/request.gleam:46-51`). Read-only is **asserted, not enforced**: a session not reporting `isReadOnly` merely adds `{"level":"warning","warning":"account_not_read_only"}` to stderr and exits 0 (`stage/screwtape/README.md:95-97`, `stage/screwtape/src/screwtape/cli.gleam:378-386`, `stage/screwtape/src/screwtape/sync.gleam:898`). Store tables are private: consumers read the JSON, never the SQLite file (`stage/screwtape/README.md:109-111`).

**6. Contract malebolge depends on.** One versioned envelope `{"version":1,"kind":<verb>,"data":…}` (`stage/screwtape/README.md:113-117`); consumers check `version` and must ignore unknown fields, since new fields/verbs/flags may appear within version 1, while removals/renames/retypes bump it (`stage/screwtape/README.md:119-129`); absent values are `null`, never omitted (`stage/screwtape/README.md:129`). Sections malebolge relies on: `mailboxes` (`:133-146`), `summary` (`:148-164`), `list` (`:166-176`), `read` (`:178-217`, incl. `provenance.email_state` at `:211-212`), `thread` (`:325-338`), `cursor` (`:347-362`), `read --after` line-delimited JSON, one envelope per line, oldest first (`:364-369`). `sync`'s document is *not* part of the contract (`stage/screwtape/README.md:109-111`), so `synced_at` cannot be used as a supported freshness signal (`stage/screwtape/src/screwtape/cli.gleam:398-414`).

### Implications for SL-012

- **Deriving (Message-ID, group).** For each agent-proposed `id`, fetch `read <id> --max-bytes 0` (`stage/screwtape/README.md:178-217`): `data.message_id` is the Message-ID list, `data.mailbox_ids` the membership, `data.keywords` the flag state. Then call `mailboxes` once per plan and map `mailbox_ids` → `{name, parent_id, role}` (`stage/screwtape/README.md:138-146`) — no per-message mailbox *names* exist, so the group must be looked up, not echoed. (inference) Build a folder path by walking `parent_id` to the root and joining names with Fastmail's IMAP separator; choose the group to name as the mailbox whose role matches the action target (inbox/archive/trash) **only if** that mailbox is in `mailbox_ids`, otherwise refuse the line.
- **Validate ids, not descriptions.** Refuse any id `read` cannot resolve (exit 2, `unknown_message`) and any `thread` id seen with `in_store: false` — the agent can legitimately surface such ids (`stage/screwtape/README.md:336-338`), and there is no Message-ID for them.
- **Refuse empty Message-ID.** `message_id: []` is a valid print (`stage/screwtape/README.md:129`); Gnus locates by Message-ID, so a line lacking one is unexecutable. (inference) Treat `len != 1` as refuse-or-operator-decides, since the header is a list and duplicates are possible.
- **Resolve at propose time, re-resolve at execute time.** Because retention drops messages moved out of configured mailboxes and evicts by count/age (`stage/screwtape/README.md:514-522`), a plan can outlive its ids. The plan must therefore store Message-ID + group as data (derived, not agent-supplied), and the elisp executor must locate by Message-ID and log a `failed` result rather than trust the stored group — the group may be stale after a move or rename.
- **IMAP name mapping is unverified.** screwtape exposes JMAP names only (`stage/screwtape/README.md:140-143`); nothing in the stage says Fastmail's IMAP path or separator, and special mailboxes may be spelled differently over IMAP. (inference) OQ-2 should be resolved empirically against the operator's `nnimap` server buffer, then frozen as a config table keyed by JMAP mailbox id, with role as the fallback — never by reconstructing names ad hoc.
- **Multiple memberships.** `mailbox_ids` can hold several ids (`stage/screwtape/README.md:162`); Gnus shows one article in one group (an article may appear in more than one). (inference) Pick the group by preference order (a mailbox the action does not target, e.g. inbox for an archive action) and record the choice in the plan line.
- **Freshness bound.** Validation is against a store up to one timer tick old (`stage/screwtape/README.md:570`); a message deleted or archived in Fastmail moments ago can still validate. (inference) That is acceptable because the executor acts on live Gnus state — but the plan's group/flag fields must be advisory and the executed record must be what Gnus reports, not what screwtape said.
- **Cost.** `list`/`thread` give no Message-ID, so deriving it costs one `read --max-bytes 0` per proposed message; cap plan lines before issuing those calls.
