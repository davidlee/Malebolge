## Thread 3 — pi extension API and jail

### Cited facts — pi extension API

1. An extension is a default-exported factory receiving `ExtensionAPI`; the documented personal location is `~/.pi/agent/extensions/hello.ts` (`pi-docs/extensions.md:15-17`). `pi --extension ./hello.ts` loads one file for a single run (`pi-docs/extensions.md:32-36`; `pi-ext-examples/README.md:8-12`), and `-e/--extension` also takes a package source without writing settings (`pi-docs/packages.md:23-27`).
2. Pi loads bare `.ts`/`.js` files and directories with an `index.ts`/`index.js` from the user or project extensions directory (`pi-docs/extensions.md:46`); npm dependencies go in a nearby `package.json` (`pi-docs/extensions.md:48`). Personal installs are recorded in `~/.pi/agent/settings.json`, project installs in `.pi/settings.json` (`pi-docs/packages.md:19`).
3. Project-supplied extensions (`.pi/extensions`, project packages) load only after a project-trust decision (`pi-docs/security.md:41`, `:47-51`); only personal and command-line extensions may answer the `project_trust` event (`pi-docs/extensions.md:50`, `pi-docs/security.md:63`).
4. TypeScript needs no build step: "Pi uses `jiti`" (`pi-docs/extensions.md:38`), and jiti resolves modules from the extension's own `node_modules` (`pi-ext-examples/with-deps/index.ts:1-6`). A package declares `pi.extensions` plus `dependencies` (`pi-ext-examples/with-deps/package.json:43-50`); host packages must be `peerDependencies`, not `dependencies` (`pi-docs/packages.md:80-90`). A local path package loads from its resolved path without copying (`pi-docs/packages.md:36`).
5. Lifecycle rule for a long-lived connection: do not open sockets/timers in the factory ("some invocations load extensions without starting a session"); start them from `session_start` or from the command/tool that needs them, and close them from an idempotent `session_shutdown` (`pi-docs/extensions.md:58-60`).
6. `session_start` fires for `startup | reload | new | resume | fork` and carries `previousSessionFile` for the last three (`pi-ext-src/types.ts:755-761`). `session_shutdown` fires with `quit | reload | new | resume | fork` before the runtime is torn down, with `targetSessionFile` on replacement (`pi-ext-src/types.ts:823-829`). `agent_end` is explicitly not a final-idle signal (retries, recovery, compaction, queued messages start another run) (`pi-docs/extensions.md:145`); `agent_settled` is the "automatic processing has stopped" point (`pi-docs/extensions.md:162-167`).
7. Reference patterns: open on `session_start`, close on `session_shutdown` with status clearing (`pi-ext-examples/gondolin/index.ts:410-425`), and `SandboxManager.initialize()` / `.reset()` on the same pair (`pi-ext-examples/sandbox/index.ts:234-295`). Cleanup must stay idempotent because cancellation, reload, replacement and exit converge (`pi-docs/extensions.md:377-379`).
8. Inbound injection, user-role: `pi.sendUserMessage(content, { deliverAs?, expandPromptTemplates? })` — "Always triggers a turn. When the agent is streaming, use deliverAs to specify how to queue the message" (`pi-ext-src/types.ts:1740-1748`). `deliverAs` is `"steer" | "followUp"`; with no `deliverAs` a send while streaming throws (`pi-ext-examples/send-user-message.ts:26-31`, `:49-51`, `:65-70`).
9. Inbound injection, custom-role: `pi.sendMessage({customType, content, display, details}, { triggerTurn?, deliverAs? })` where `deliverAs` also accepts `"nextTurn"` (`pi-ext-src/types.ts:1735-1738`); `triggerTurn: true` starts a turn, as the file-trigger example does (`pi-ext-examples/file-trigger.ts:162-169`).
10. A run started by `sendUserMessage` arrives in `before_agent_start` as `messageType: "user"` with `prompt`; a run started by `sendMessage(..., {triggerTurn:true})` arrives as `"custom"` with `message` and no `prompt`, and `messageType` exists so an extension can skip runs it started (`pi-docs/extensions.md:216`, `pi-ext-src/types.ts:940-957`).
11. Busy/idle state is available as `ctx.isIdle()` and `ctx.hasPendingMessages()` (`pi-ext-src/types.ts:348`, `:356`). `ExtensionCommandContext.waitForIdle()` is command-only and must not be used from lifecycle handlers (deadlock) (`pi-docs/extensions.md:329-330`, `pi-ext-src/types.ts:406`). The `ReplacedSessionContext` variants of `sendMessage`/`sendUserMessage` return promises (`pi-ext-src/types.ts:443-451`), unlike the fire-and-forget `ExtensionAPI` ones (`pi-ext-src/types.ts:1735-1748`).
12. `pi.registerTool(def)` registers a model-callable tool (`pi-ext-src/types.ts:1675-1677`); the definition needs `name`, `label`, `description`, a TypeBox `parameters` schema, and `execute()` returning `AgentToolResult` (`pi-ext-src/types.ts:579-591`, `:649-656`). The result requires model-facing `content` and `details` (`details: undefined` when empty); throwing produces a failed result; `terminate: true` skips the follow-up only when every tool in the batch agrees; `outputSchema`/`structuredContent` for data results; `isError: true` for failures that still carry data (`pi-docs/extensions.md:247-259`).
13. Minimal concrete tool shape, including `promptSnippet`, `promptGuidelines`, and `details` (`pi-ext-examples/dynamic-tools.ts:33-46`); a tool may also be registered later from `session_start` (`pi-ext-examples/dynamic-tools.ts:51-54`, `pi-docs/extensions.md:299`). `exposure` (`direct`/`model-only`/`codemode`/`deferred`/`hidden`) controls model reachability (`pi-docs/extensions.md:267-273`).
14. Slash commands: `pi.registerCommand(name, { description, handler, getArgumentCompletions? })`, handler receives `(args, ctx)` with `ExtensionCommandContext` (`pi-ext-src/types.ts:1684`, `pi-ext-examples/send-user-message.ts:18-35`, `pi-ext-examples/commands.ts:16-24`). CLI flags come from `registerFlag` + `getFlag`, and are only readable after startup, so resolve them lazily in `session_start` (`pi-ext-src/types.ts:1696-1712`, `pi-ext-examples/ssh.ts:123-126`, `:184-199`).
15. Background async work has precedent: `fs.watch` opened inside `session_start` with a synchronous read on each event and a `notify` when watching begins (`pi-ext-examples/file-trigger.ts:155-179`), and single-flight lazy start of an expensive resource via a cached promise (`pi-ext-examples/gondolin/index.ts:375-408`). Guidance: do not do slow work on streaming events (`pi-docs/extensions.md:214`); use `ctx.signal` for work owned by an active turn, noting idle events often have none (`pi-docs/extensions.md:238`).
16. Connection status in the UI: `ctx.ui.setStatus(key, text|undefined)` for footer text and `ctx.ui.notify(msg, "info"|"warning"|"error")` for one-shot notices (`pi-ext-src/types.ts:160-166`), as `setStatus` on `session_start`/`turn_end` (`pi-ext-examples/status-line.ts:87-105`) and `setStatus` + `notify` on connection-like state (`pi-ext-examples/ssh.ts:197-198`, `pi-ext-examples/gondolin/index.ts:380-396`). Status is terminal-only; guard with `ctx.mode === "tui"` / `ctx.hasUI` because JSON/print modes have no UI (`pi-docs/extensions.md:363-366`).
17. Session identity available to an extension: `ctx.cwd` and `ctx.sessionManager` (read-only) (`pi-ext-src/types.ts:332-335`), `ctx.sessionManager.getSessionFile()` (`pi-ext-examples/handoff.ts:112`), and `pi.getSessionName()`/`setSessionName()` (`pi-ext-src/types.ts:1757-1761`). Session files by default live under `~/.pi/agent/sessions/`, grouped by working directory, and are resumable (`pi-docs/sessions.md:50`, `:14`); `/session` shows file, ID, counts (`pi-docs/sessions.md:16`). No session-id accessor appears in the staged `types.ts` — `ReadonlySessionManager` is imported from another module (`pi-ext-src/types.ts:76`), so `getSessionFile()` is the concrete, visible identity handle.
18. Durable pairing state should go through `pi.appendEntry(customType, data)` (not sent to the LLM) and be reconstructed from `ctx.sessionManager.getBranch()` during `session_start` (`pi-ext-src/types.ts:1750-1751`, `pi-docs/extensions.md:337-349`); `plan-mode` does exactly this, appending a `"plan-mode"` entry and reading it back at `session_start` (`pi-ext-examples/plan-mode/index.ts:117`, `:344-353`).
19. Inter-process/event mechanisms: `pi.events` is an in-process `EventBus` for extension-to-extension messages (`pi-ext-src/types.ts:1920-1921`, `pi-docs/extensions.md:186`, `pi-ext-examples/event-bus.ts:118-139`) — it cannot carry a daemon connection. The closest existing cross-process bridge is `subagent/`, which spawns a child `pi --mode json -p --no-session` and parses its ndjson output (`pi-ext-examples/subagent/index.ts:298`, `:344-361`); that is parenting a child, not dialing a socket. RPC mode forwards UI only (`pi-docs/extensions.md:365`, `pi-ext-examples/rpc-demo.ts:1-18`). (`pi-docs/durable-README.md:224-243` describes a *different* extension model — pi-durable's registry — not the coding agent's.)

### Cited facts — jail

1. The satan-mcp socket is mounted as a directory, read-only, with its env forwarded: `(try-readonly "/run/user/1000/satan/mcp")`, `(try-fwd-env "XDG_RUNTIME_DIR")`, `(try-fwd-env "SATAN_MCP_SOCKET")` (`jailed-agents.nix:171-175`). Rationale: a file bind pins the inode `satan-mcp-start` replaces, and a writable directory would let the jail replace the socket and impersonate the server (ISS-042) (`jailed-agents.nix:168-170`). It is offered to consumers as an exported option set, `inherit satanMcpOptions` (`jailed-agents.nix:605-606`), applied through the maker's `extraOptions` (`jailed-agents.nix:442`, appended last at `:557`; used this way in `flake.nix:82`).
2. `mountLaunchDir` on: `--bind "$PWD" "/workspace/$(basename "$PWD")"` plus `--chdir` there; off: bind nothing, `--chdir "$HOME"` (`jailed-agents.nix:232-239`, DEC-078 comment `:228-231`). That is the only place the project is bound, and it is read-write. A read-only variant changes exactly one word: `--ro-bind` instead of `--bind` — the same two flags the workspace-deps binder already selects between (`workspace-binds.nix:68-71`), and binds are applied in argv order so mount order matters (`jailed-agents.nix:542-544`).
3. Home is the profile's persisted home: `profileOptions p home = [(jail.combinators.persist-home home)] ++ network-if-set` (`jailed-agents.nix:265-269`), with names `agent` / `agent-research` / `agent-offline` (`jailed-agents.nix:245-263`). That home is writable — `persist-home gives it a writable ~/.cargo` (`jailed-agents.nix:343`) — so `~/.pi/agent/extensions/` (`pi-docs/extensions.md:46`) and `~/.pi/agent/settings.json` (`pi-docs/packages.md:19`) persist inside the jail. pi also gets a generated **read-only** `~/.pi/agent/models.json` for the gateway (`jailed-agents.nix:13-15`, `:179-183`), and the gateway key travels over an `--args FD`, never argv (`jailed-agents.nix:19-22`, `:392-397`). The read-only-bind-into-home pattern to copy is `hostDoctrineOptions`: `try-ro-bind` a host directory at a jail path plus `add-path` (`jailed-agents.nix:348-357`), with the ordering caveat that a runtime bind must follow the persisted-home bind or be covered by it (`jailed-agents.nix:132-135`).
4. Profiles differ only in network and home/identity defaults: `specDev` = network, `agent`, sandboxGitIdentity; `research` = network, `agent-research`, no sandboxed identity; `offline` = no network, `agent-offline` (`jailed-agents.nix:245-263`). `network` is data, not caller-overridable (DEC-076) (`jailed-agents.nix:241-244`), and is applied as `jail.combinators.network` (`jailed-agents.nix:267-269`).
5. Combinator signature pattern to copy: a namespaced set (`jail.combinators`, re-exported at `jailed-agents.nix:590`) of nullary/combinator factories — `try-readonly path`, `try-readwrite path`, `try-ro-bind src dst`, `try-fwd-env name`, `add-path`, `add-runtime`, `unsafe-add-raw-args`, `persist-home`, `network`, `add-pkg-deps` (`jailed-agents.nix:171-175`, `:348-357`, `:365-366`, `:392-397`). Policy grouping is a function over a combinator set: `posture = { ... }: c: baseJailOptions c ++ ... ++ [(c.add-pkg-deps commonPkgs)]` (`jailed-agents.nix:407-428`), applied per jail at `:539-558`.

### Answers bearing on open questions

**OQ-2 (authentication).** The mount authorises *use*, not *identity*. Every jail runs as the same uid, with an emptied environment, bwrap as PID 1 (`jailed-agents.nix:40-50`), so a peer-credential check of the kind the runner control socket uses — directory must be owned by this uid and 0700, socket chmod 0600, else refuse (`src/runner/control.ts:314-323`, `:343-344`) — passes for *any* jail with the mount and distinguishes nothing. Several jails sharing one read-only socket directory (the ISS-042 shape, `jailed-agents.nix:168-175`) therefore cannot be told apart by the mount alone: any of them can dial and claim another's pairing. Identity the jail *could* present, in increasing strength: facts it already has (cwd `/workspace/<project>` via `ctx.cwd`, `pi-ext-src/types.ts:333`; session file via `getSessionFile()`, `pi-ext-examples/handoff.ts:112`); an env var the combinator forwards per jail, exactly as `try-fwd-env` does for `SATAN_MCP_SOCKET` (`jailed-agents.nix:173-175`); or a per-jail secret file bound read-only by the combinator (inference, following `hostDoctrineOptions`, `jailed-agents.nix:348-357`). Inference: a pairing token is needed, and it must be persisted with the pairing because a conversation id is meaningful only within one profile's store and socket (`src/protocol.ts:18-20`).

**OQ-3 (turn semantics, pi side).** pi gives one useful split: `sendUserMessage` always starts a turn and throws when busy without `deliverAs` (`pi-ext-src/types.ts:1740-1748`, `pi-ext-examples/send-user-message.ts:26-31`), while `sendMessage(..., { triggerTurn: false })` records a custom message, visible or not, without starting a turn (`pi-ext-src/types.ts:1735-1738`; `display` controls the transcript, `pi-ext-examples/file-trigger.ts:162-169`). So "reply starts a turn, note does not" maps onto two API calls, and mid-run arrivals map onto `steer` vs `followUp` vs `nextTurn`. Two caveats: a *run* is several model turns and may re-enter after `agent_end` (`pi-docs/extensions.md:62-78`, `:145`), so hop counting must count runs or bridge messages, not `turn_end`; and pi offers no reply correlation — request ids have to ride in the tool result `details` and in the injected message text (`pi-ext-src/types.ts:649-656`, `pi-docs/extensions.md:247-249`). Inference: the loop bound belongs in the daemon or the tool, not in prompt wording.

**OQ-6 (extension home and packaging).** The maker takes no agent-argument parameter (`jailed-agents.nix:437-478`), so `pi --extension` (`pi-docs/extensions.md:32-36`) cannot be injected at the launcher; the loadable paths are the ones pi discovers. Three shapes, all supported by staged facts: (a) drop the extension into the persisted home's `~/.pi/agent/extensions/` (`pi-docs/extensions.md:46`) — writable, survives restarts, but shared by every jail of that profile and writable by any of them (`jailed-agents.nix:265-269`, `:343`); (b) declare it in a `settings.json` package entry (`pi-docs/packages.md:19`) or ship it as a local-path package (`pi-docs/packages.md:36`, manifest at `:59-70`) and bind that directory read-only over the home path in `extraOptions` (`jailed-agents.nix:557`), following `hostDoctrineOptions` (`:348-357`) — immutable in-jail, versioned with the host; (c) place it under the project's `.pi/extensions`, which requires project trust and lets repo content inject executable code into the bridge jail — inference: reject for a bridged jail (`pi-docs/security.md:41`, `:47-51`). A bridge extension should not be a project extension for that reason.

**OQ-7 (posture).** Prompt text can be set three ways: mutate `event.systemPromptOptions.sections[...]` in `before_agent_start` (keeps pi's structured prompt and transcript delta — `pi-ext-examples/prompt-customizer.ts:40-48`, `pi-docs/extensions.md:216`); return `systemPrompt` to replace the whole prompt for that run, which is what `preset.ts` does to add mode instructions (`pi-ext-examples/preset.ts:385-392`, `pi-docs/extensions.md:216`); or set the active tool set (`pi.setActiveTools`, `pi-docs/extensions.md:299`), which is how plan-mode enforces read-only. Posture can also be bound to a CLI flag resolved at `session_start` (`pi-ext-src/types.ts:1696-1712`, `pi-ext-examples/ssh.ts:184-199`) and persisted with `appendEntry`, so "which posture" is recoverable after resume (`pi-docs/extensions.md:337-349`). Inference: posture belongs in a prompt section keyed by `customType` of the injected bridge message, and `messageType === "custom"` lets the extension apply the bridge framing only to messages it delivered (`pi-docs/extensions.md:216`).
