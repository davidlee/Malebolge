### Cited facts

1. The daemon socket path is `$MALEBOLGE_SOCKET`, else `<XDG_RUNTIME_DIR>/satan/durable/<profile>/durable.sock` (config.ts:123-125), and `resolveConfig` refuses a path whose parent directory is not named for the profile (config.ts:272, config.ts:289). The directory is created with default mode — `mkdirSync(dirname(socketPath), {recursive:true})`, no `mode` (daemon-start.ts:234) — and `serveUnix`/`claimUnix` never `chmod` the socket (unix-socket.ts:88-107, unix-socket.ts:119-127). Only the runner's control socket does: `prepareDirectory` + `chmod(socketPath, 0o600)` (runner/control.ts:330, runner/control.ts:344), which is the existing precedent for a mode-restricted listener.
2. Listening replaces only a *stale* socket: EADDRINUSE probes the path, a live server is `SocketInUse`, a stale file is unlinked and re-listened (unix-socket.ts:88-107).
3. First-frame dispatch: `parseConnectionMessage` (protocol.ts:369) tries `parseFirstLineFrame` (protocol.ts:352) — a switch on `type` over `attach`/`list`/`topic` (protocol.ts:352-362) — and falls back to `clientMessage` (protocol.ts:381). `daemon.ts` holds one table keyed by `FirstLineFrame["type"]` (daemon.ts:241), and the mapped type makes a frame without a row a compile error (daemon.ts:241-252). `firstLine` routes through it (daemon.ts:265-292); `laterLine` refuses *any* first-line frame on a bound connection with `already attached to conversation N` (daemon.ts:294-310).
4. Frames that exist: client→daemon `input`/`abort`/`compact`/`orient` (protocol.ts:27-31), first-line `attach` (protocol.ts:52), `list` (protocol.ts:67), `topic` (protocol.ts:75); daemon→client `attached` (protocol.ts:56), `conversations` (protocol.ts:96), `topics` (protocol.ts:112), `error` (protocol.ts:33), plus pi-durable `watchEvents` agent events (daemon.ts:165-170).
5. There is **no per-connection verb restriction**: every connection is served by the same `serve()`/`startConnection` and, once bound, may send any `ClientMessage` (daemon.ts:110-135, daemon.ts:358-375). There is also **no second listener in this process**: the only `serveUnix` call in the daemon is `serve()` (daemon.ts:383, called from daemon-start.ts:239); the other listener in the repo is the runner's control socket (runner/control.ts:330). The satan-mcp socket is a *client* connection, not served here (satan-tools.ts:236, reconnecting-client.ts:180).
6. A post is delivered by opening the target conversation and submitting one input with `whenBusy: "followUp"`, a namespaced `requestId`, and an entry of kind `satan.post` carrying the payload (threads/task.ts:157-172). Deliver waits for the turn unbounded (`endingOf(await submission.wait(ctx))`, threads/task.ts:173) — unlike a wake, which bounds its wait by the ceiling (wake/task.ts:417-445). If the target is busy the input is queued as a follow-up rather than refused (threads/task.ts:166; harness policy `followUpMode: "one-at-a-time"` session.ts:178-181).
7. The post envelope the model reads is inline-built: `<post from="12" topic="inbox"><intent>…</intent><context>…</context></post>`, with `<post-failed …>` and `<family-reaped …/>` (threads/task.ts:99-117). Values are interpolated unescaped, though `escapeXml` exists (xml.ts:3).
8. Posts are queued **durably**, not in memory: the post is a pi-durable task owned by its recipient, created backgrounded in the transcript (threads/task.ts:87-96), so it survives a daemon restart and `harness.resume()` (session.ts:205-206). Idempotency comes from `requestId` `post:<taskId>:` (threads/task.ts:84) and its lookup via `tx.submissionByRequest` (threads/task.ts:236-245).
9. Admission: a post is refused if the target is the caller, unknown, unindexed (a task's conversation), or outside the caller's talk set (admission.ts:149-170); the caller must be indexed and its turn must have an origin, and a reaped origin is refused (admission.ts:122-146). Refusals are `Refusal` (admission.ts:30) mapped to an `isError` tool result by `attempted` (threads/tools.ts:466-475).
10. Caps are counts of *live posts per origin*, not hops: `FAMILY_CAP = 4` active posts per origin and `GLOBAL_CAP = 12` daemon-wide (admission.ts:24, admission.ts:27), decided purely by `verdict` (caps.ts:95-116) from `familiesOf` over `harness.inspect` (threads/tools.ts:353-360). A crossing reaps the family (own → refusal, other → admitted with a tombstone, threads/tools.ts:300-315, threads/tools.ts:371-386). The origin that is counted **propagates through posts**: a `satan.post` entry's origin is the origin it carries (admission.ts:70-78), so a post-turn's next post counts under the cascade's first human input.
11. Talk sets: `TALK_SETS` maps profile → toolset → set (toolsets.ts:71-74; `room` has only `interactive: "interactive"`, `host` none), enforced by `requireSameTalkSet` (toolsets.ts:81-99), wrapped as a `Refusal` by `refuseOutsideTalkSet` (admission.ts:36-45). A conversation's mode is fixed at creation and stored in the index entry as `toolset` (topics.ts:36-41), written by `writeCreated` inside the creating commit (topics.ts:135, conversations.ts:165-190) and turned into installed extensions by `selectionOf(toolsetList(...))` (conversations.ts:189-191). A new mode costs one `CATALOG` entry (toolsets.ts:24-40) plus `PROFILE_TOOLSETS` (toolsets.ts:62-65) and `TALK_SETS` (toolsets.ts:71-74) rows, plus a builder in `daemon-extensions.ts:35-57`; `allowedNames` (toolsets.ts:101) makes installation automatic and the startup reconcile (session.ts:152-176) re-derives every stored list.
12. Turn origin envelopes: wake renders `<wake fired_at="…" late_by="…" class="…" scheduled_by="…">…<intent>…</intent><payload>…</payload><percept>…</percept></wake>` (wake/task.ts:183-197) and submits it with `whenBusy:"followUp"` (wake/task.ts:429-437). A human turn has no envelope at all — `UserEntry`/`ResetEntry` are the origin directly (admission.ts:71-73).
13. Conversation open/resume by id goes through `Conversations.open` (conversations.ts:305-326): `existing` → `resolveExisting` (commit read + `harness.conversation`, conversations.ts:118-133), `new` → `create` with `agent: defaults` (conversations.ts:200-207); `watch` is the only route to the harness for output (conversations.ts:327) and `bind` writes the snapshot then streams every event as one ndjson line (daemon.ts:139-172).
14. Untrusted-data framing helpers are thin: only `escapeXml` (xml.ts:3) and the prompt-section tag convention (`section(..., {tag:true})`, threads/extension.ts:68). There is no existing "quote foreign text as data" helper; mail frames *validated* envelopes rather than foreign prose (mail/screwtape.ts:171-208).

### Naming precedents

- Verbs/frames: `attach`, `list`, `topic`, `attached`, `conversations`, `topics`, `error` (protocol.ts:52-112); typed as `…Message` + `parseFirstLineFrame` + one `FIRST_LINE` row. A bridge verb should read `pair` → `paired`, `post`, `receive` → `received`.
- First-line vs bound split: `FirstLineFrame` vs `ClientMessage` (protocol.ts:346, protocol.ts:27); refusal class `FrameRefused` with the `"<frame>: <problem>"` wording (protocol.ts:117-129).
- Modules: `src/unix-socket.ts` (generic server), `src/unix-socket-transport.ts` (client transport), `src/reconnecting-client.ts` (client that outlives a restart), `src/request.ts` (one-frame request/reply client), `src/attach.ts`/`attach-main.ts` (long-lived client).
- Domain: `POST_KIND = "satan.post"`, `WAKE_KIND = "satan.wake"` (threads/task.ts:32, wake/task.ts:45) → a bridge entry/task kind would be `satan.bridge`; `postRequestId` → `bridgeRequestId`.
- Extensions/toolsets: `threadsExtension` with `THREADS_SECTION` and `thread_post`/`thread_start`/`thread_fork` (threads/extension.ts:61-69, threads/tools.ts:479) → a `bridge` extension with `bridge_post`, mirroring the toolset name `interactive`/`mail` (toolsets.ts:19-20).
- Caps: `FAMILY_CAP`/`GLOBAL_CAP` + `Verdict` (`admit`/`reap-own`/`reap-other`) (admission.ts:24-27, caps.ts:66-71).

### Answers bearing on open questions

**OQ-1 (second socket vs filtered mode; wire shape).** A second listener is cheap mechanically — `serve(options)` is a pure function of a path and a connection callback (daemon.ts:382-386), `claimUnix` already handles path claim/stale replace (unix-socket.ts:88-107), and `startDaemon` has one place to start and one to stop it (daemon-start.ts:239, daemon-start.ts:280-287). Inference: the restricted verbs want a *different* table, so the honest shape is a second `serve*` (e.g. `serveBridge`) with its own `FIRST_LINE`-style map, since `FIRST_LINE` is a module constant keyed by one union (daemon.ts:241) and `startConnection` hardwires `bind`/`act` (daemon.ts:139, daemon.ts:110). A filtered mode on the one socket would need a new per-connection capability field threaded through `ServeOptions`/`Connection` (daemon.ts:26-33, daemon.ts:38-55) and a check in `act` (daemon.ts:110) and `laterLine` (daemon.ts:294) — more edits than a second listener, and it weakens the invariant that the full socket is one protocol. Reusing ndjson frames is free: `encodeLine`/`lineSplitter` are shared by every socket already (ndjson.ts:78, ndjson.ts:6).
Permission cost favours the second socket too: `serveUnix` leaves the socket at the umask default (unix-socket.ts:119-127), while the jail mount must be a *directory* (ISS-042 in slice-009), so a bridge socket in its own directory can be `chmod`-ed like the runner's (`runner/control.ts:344`) without touching `durable.sock`. `inProfileDir` would refuse a path outside a `<profile>` directory (config.ts:272), so the bridge socket must be `<runtime>/satan/durable/<profile>/…` or that check must learn an exception.

**OQ-3 (turn semantics).** "Every message starts a turn" is the existing behaviour of one submit (threads/task.ts:157-172); "only some" needs a second letter in the payload union and a branch in `placed`, which is a small, precedented change (`PostInput` already has three letters, threads/task.ts:35-56). Correlation is already solved: `requestId` namespaces a reply per post (`post:<taskId>:`, threads/task.ts:84), and correlation back to the sender is the `<post from="…">` attribute (threads/task.ts:103) plus `post-failed post="<id>"` (threads/task.ts:110). A reply correlation would be a new field on the incoming envelope, not a new mechanism.

**OQ-4 (loop bound).** Reuse is cheap and already semantics-complete: caps count live posts per *propagating* origin, so a pi↔SATAN exchange shares one family and is bounded at 4 active / 12 global with an explicit refusal text (`Refusal`, admission.ts:30; `reapedRefusal`, tombstones.ts:54). The origin kinds are closed at `human`/`wake` (origin.ts:9-17, `isOrigin` origin.ts:30-41), so a `bridge` origin needs an edit there, and the *reset by an operator turn* falls out for free: a human `UserEntry` becomes a new origin (admission.ts:71-73), hence a new family. Expensive parts: hops/rate are not modelled anywhere (caps.ts has no time dimension, caps.ts:95-116), and a bridge message injected as a `satan.post`-kind entry must satisfy `isOrigin` and `dataOf(entry,"origin",…)` or `callerOrigin` throws (admission.ts:70-78, admission.ts:78-95). Inference: the cheapest correct OQ-4 answer is "reuse admission verbatim, add `bridge` as an origin kind" — a rate cap would be a new pure module beside `caps.ts`.

**OQ-5 (mode and talk set).** Adding a `bridge` toolset is bounded: one `CATALOG` row (toolsets.ts:24-40), one `Toolset`/`DaemonToolset` union widening (toolsets.ts:9-12), `PROFILE_TOOLSETS.room.allowed` (toolsets.ts:62-65), one `TALK_SETS` row (toolsets.ts:71-74), one `daemon-extensions.ts` builder (daemon-extensions.ts:35-57), and — because the reconcile refuses any stored toolset the profile does not allow (session.ts:117-137) — a bridge toolset must be added *before* any conversation stores it, or startup throws. Note `ROOM_ONLY` strips `tasks`/`threads` on host (toolsets.ts:42), so a bridge set on `room` only is expressible. `TALK_SETS` is what keeps reach from leaking: a bridged conversation could be given its own set, and `requireSameTalkSet` would then refuse thread_post between it and `interactive` conversations (toolsets.ts:81-99) — but that also *breaks* the bridge's own posting unless the bridge path bypasses `admitPost` or the two share a set. The existing `mail` toolset is the precedent for "own set, own persona files, no talk set at all" (toolsets.ts:24-40, README of talk sets at toolsets.ts:69-74).

**OQ-8 (queue durability).** Durability is free if bridge messages ride `createPostTask`: the task row is in SQLite, `resume()` replays it (session.ts:205-206), `whenBusy:"followUp"` queues behind a running turn (threads/task.ts:166), and a settle writes `post-failed` back to the sender (threads/task.ts:178-198). An in-memory queue on the bridge connection would be strictly *less* work but would lose messages across daemon restart and pi reconnect, and would have to re-implement the sender notification that `failed`/`noticeOf` already provide (threads/task.ts:178-215). Inference: the only thing a durable queue cannot express today is "deliver to a *pi client* rather than a conversation" — the recipient here is a conversation, and the pi extension is a client of it, so the natural split is: pi→malebolge is a post (durable), malebolge→pi is a *watch* of the bound conversation stream (conversations.ts:327, daemon.ts:165-170), which is replayable from the snapshot (daemon.ts:167) — that is exactly how `attach` already survives reconnect.
