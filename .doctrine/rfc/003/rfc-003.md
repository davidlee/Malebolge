# RFC-003: Conversation domain model: identity, protocol, mode, capability, place, history, turn origin

## Context

### Status of this document

Open, drafted 2026-10-28. The operator judged the taxonomy below
"directionally right" and in need of refinement. The aim is to move towards
it incrementally in the next slice (threads: start, fork, post), so that
slice does not deepen the current model. An RFC asserts no canon: each
decision binds only once a slice's design adopts it.

Evidence comes from this repo at `be96446` and `~/satan-corpus` at `8060231`
(`prompts/`, `system/`), read 2026-10-28.

### Why now

The goal is SATAN holding many conversation threads in different contexts,
with different prompts and tools, that start, fork and message each other.
The next slice adds the first of those verbs. Each one asks questions the
current model answers badly: what a fork inherits, what a post is, and who may
reach whom. The answers depend on how topic, toolset, system prompt and
history relate. That relation is currently implicit and partly contradictory.

### How the pieces fit today

```
topic ──► cwd
      └─► default toolset ──► fixed in the conversation's index entry at creation
                               (src/topics.ts IndexEntry; DEC-025)
toolset (DEC-029) = an ordered extension list, prompt included (src/toolsets.ts CATALOG)
  interactive: persona, project_context, skills, cwd, conversation,
               coding-tools, grep, tasks (room only), satan
  mail:        mail-persona, conversation, mail
  job:         job-tools, job-guard (runner)
persona (src/persona.ts) = system/scaffold.txt + prompts/<mode>.txt
                           + prompts/env/<profile>.txt (interactive only)
history = pi-durable transcript; a fork copies it as of the fork point
turn    = a human's input, or a wake (prompts/wake.md inside a <wake> envelope)
```

### What does not fit

1. **The scaffold contradicts every daemon conversation.**
   `system/scaffold.txt` is prepended to every mode prompt
   (satan-corpus `AGENTS.md`). It mixes three things:
   - identity and stance: who SATAN is, evidence discipline, the memory model;
   - a batch protocol: JSONL only, end with `satan_final`, never prose;
   - write boundaries and memory surfaces naming specific tools
     (`inbox_append`, `memory_mark`, `proposal_stage`, …).

   `prompts/interactive.txt` and `prompts/mail.txt` each open with
   "Precedence — read this first" to undo the second and third. Part of every
   daemon prompt is text that is wrong for it, followed by text retracting it.
2. **Prompts restate the tools.** `interactive.txt` lists tool categories and
   says "All tools are available to you". `mail.txt` lists the tools it lacks. The scaffold's own
   "Tool discipline" says the manifest is the canonical tool catalog.
3. **Environment text describes a tool, not a persona.** `env/room.txt` and
   `env/host.txt` say where the coding tools run. Mail has no environment file
   because its tools run on the host whatever the profile (DEC-028). Some
   extensions already carry their own prose: `mail` (`src/mail/extension.ts`,
   the untrusted-data framing), `cwd`, `project_context`, `skills`,
   `conversation`. Coding tools and SATAN tools do not.
4. **"Toolset" names a mode.** Since DEC-029 a toolset is prompt plus tools.
   The corpus calls these modes ("You are SATAN in `morning` mode"; "In this
   mode, mail triage"). DEC-029 kept the name knowing it now covers the prompt.
5. **Turn origin is unmodelled, and is about to grow.** A turn starts from a
   human, a wake, or (next slice) a post from another thread. Wakes have an
   ad hoc pattern: an envelope element with provenance (`fired_at`,
   `scheduled_by`, `intent`, `percept`). Interactive orientation is a
   first-turn tool call that compaction folds away (IMP-016).
6. **History is coupled to capability, and nothing says so.** A transcript
   holds tool calls and results made under one mode. A fork into another mode
   would inherit calls to tools it lacks, and content (for example untrusted
   mail) its new mode should never have seen. The system prompt, meanwhile,
   re-renders from current files on every request (`src/persona.ts`).

## Discussion

### Proposed taxonomy

| Concept | What it is | Varies with | Source today | Source proposed |
|---|---|---|---|---|
| **Identity** | who SATAN is: stance, evidence discipline, memory model | nothing: constant | first half of `scaffold.txt` | `system/identity.txt` (split from the scaffold) |
| **Protocol** | who reads the output and how the run ends: a human reading prose, or a harness reading JSONL and `satan_final` | run kind (daemon conversation, batch run) | `scaffold.txt` Protocol, retracted by each daemon mode | one file per protocol, chosen by run kind |
| **Mode** | what the conversation is for: purpose and policy, plus the extensions it gets | the conversation, fixed at creation | "toolset" (DEC-029) | rename toolset → mode; the mode prompt holds only purpose and policy |
| **Capability** | a tool and the prose that describes it: where it runs, what it may write, how to read its output | which extensions the mode names, and the profile | scattered: scaffold write boundaries, `env/*.txt`, mode prompt tool lists | a section contributed by each extension, so the prose appears exactly when its tool does |
| **Place** | where the conversation works: topic, cwd, project context | topic | topic record (`cwd`, default toolset) | unchanged; the topic proposes a mode and does not own one |
| **History** | the transcript, including tool calls under its mode | the conversation; forks copy it | pi-durable | unchanged; it is bound to the mode it was made under (see Forks) |
| **Turn origin** | why this turn started, with its provenance | each turn | a human's input; the `<wake>` envelope | one envelope family: human, wake, post, and orientation (IMP-016) |
| **Reach** | which modes a conversation may cause to run, by starting or posting into them | profile policy | none | a closed table in code beside `PROFILE_TOOLSETS` |

Assembled system prompt, proposed:

```
identity ─ protocol(run kind) ─ mode prompt ─ capability sections, one per extension, in mode order
                                              (env, write surfaces, untrusted-data framing, …)
place sections: cwd, project_context, conversation
per turn: origin envelope (human | wake | post | orient)
```

The "Precedence" sections then disappear, and no prompt states a tool its
manifest lacks.

### Reach is authority

Whatever a conversation can reach becomes part of its own capability.
Starting a thread or posting into one runs that thread's mode on the caller's
behalf. So the authority boundary is reach, not any one verb's arguments.

Modes do not form a chain. Interactive lacks mail tools, and mail lacks coding
tools. "Post only to the same or a narrower mode" therefore has no meaning.

**Talk sets** (operator, 2026-10-28): the simplest useful limit is to draw a
line around a set of modes and say "these can talk". Within a set,
conversations may start, fork and post into each other. Across sets, nothing
flows. A set is a trust domain: its members' combined capability is what any
one of them can reach, and the operator accepts that when defining the set.
The sets are closed and defined in code, as `PROFILE_TOOLSETS` is.

This replaces an earlier draft's pairwise reach table (which mode may reach
which). A partition is simpler to state, check and audit, and a pairwise
table bought nothing the threads slice needs.

Mail mode belongs to no talk set (RSK-002). It reads foreign text, so it is a
quarantined reader ("possibly a zombie; you don't talk to zombies"). It talks
only to the operator. Its transcript and outputs are quarantined derivatives.
Starting mail from interactive was considered and dropped: it has no use worth
the exposure.

### Forks

A fork copies history, and history is bound to its mode (fit problem 6).
Options:

- **A. A fork keeps its parent's mode.** Simple and coherent. Changing mode
  means starting a fresh thread with a brief.
- **B. A fork may change mode where reach allows it.** Flexible, but the new
  mode inherits calls to tools it lacks, and content its policy might exclude.

Talk sets settle the security side: a fork stays within its parent's set.
Whether a fork may change mode within the set is left to design. History
coherence argues for A as the default. A forked mail conversation stays mail
(RSK-002).

### Posts

A post is a turn whose origin is another conversation. It renders as an
envelope like `<wake>`, carrying the sender's id and mode. The sender's id is
also the reply address, so the index needs no "started by" relation. Open:
whether a recipient treats a post as an instruction (a peer asking) or as data
(material to weigh). Talk sets mostly settle it: posts arrive only from
members of the same trust domain, so a post is a peer's message.

### Bounds

Starting and posting both spend model turns. They need a live-thread cap, and
a cap on post-triggered turns (by chain depth or by rate), so two threads
cannot trigger each other without end. These belong to the threads slice,
not to this model.

### Incremental path

None of this has to land at once. Each step stands alone:

1. **Rename toolset → mode** in code and records (it is a name only; stored
   index entries keep a migration alias if needed).
2. **Capability prose moves to extensions:** `env/<profile>.txt` becomes the
   coding-tools section; SATAN's write surfaces move to the `satan` section
   (or its MCP tool descriptions).
3. **Split the scaffold** in satan-corpus into identity and batch protocol.
   Daemon modes stop prepending the batch protocol and drop their
   "Precedence" sections. The batch harness keeps identity + protocol + mode,
   which leaves batch runs unchanged.
4. **Talk sets, fork rule, post envelope:** the threads slice.
5. **Orientation as a turn envelope** (IMP-016).

Steps 1, 2 and 4 are malebolge. Step 3 changes satan-corpus and touches the
satan batch harness (satan repo). Step 4 is the next slice's core. Steps 1–3
and 5 land incrementally, as the work touches them (operator, 2026-10-28,
OQ-6): no step is done for its own sake.

## Outcome

Open. Operator answers of 2026-10-28 are recorded inline; the rest are to
settle during the threads slice's design.

- **OQ-1:** Is "mode" the right name for today's toolset, and is purpose plus
  policy everything a mode prompt holds? *Open.*
- **OQ-2:** Does the topic keep proposing a default mode, or does every start
  name one? *Open.*
- **OQ-3:** Fork rule. *Answered:* authority is talk sets, closed sets of
  modes whose members may start, fork and post into each other (Reach is
  authority). Whether a fork may change mode within its set is left to
  design; history coherence argues against.
- **OQ-4:** Post semantics: an instruction from a peer, or data to weigh?
  *Mostly settled by talk sets:* a post comes from a trusted peer.
- **OQ-5:** First talk sets. *Answered:* interactive → mail has no use worth
  the exposure; mail belongs to no set. The threads slice's set is the daemon's
  own conversations. The interesting talk crosses harnesses (OQ-8).
- **OQ-6:** Where the scaffold split lands. *Answered:* incrementally, as the
  work touches each piece.
- **OQ-7:** Where do quarantined derivatives live, and how does the lexical
  exception reach them (RSK-002 gap 3)? *Open; not needed by the threads
  slice.*
- **OQ-8:** Talk across harnesses: SATAN with the patch runner (runner jobs),
  and pi-durable conversations with the gptel batch runs (`tick-agent` and the
  other satan-corpus modes). Each crosses a process and a security boundary;
  the runner executes code under its own policy. *Open, to be decided later;
  out of the threads slice.*
