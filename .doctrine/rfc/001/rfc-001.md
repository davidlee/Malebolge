# RFC-001: A shared kernel tier for the room session: advice to satan:SL-027 inq-2

## Status of this document

Advice, not authority. It is written by an agent that reviewed this repository's
structure (RV-001) at the request of the user, in response to a question in
another project, and it is handed to whoever answers satan:SL-027's `inq-2`. The
decision belongs to satan:SL-027 (in the SATAN repo: `malebolge daemon vm mode:
coding tools in the room`, design run, `inquiring`). This RFC's standing is
tier-5 evidence: it informs, it does not instruct.

It deliberately does **not** edit satan:SL-027. satan:SL-027's `inq-2` reads:

> Shared room module: what moves out of `src/runner` (`RoomConnection`, `Launch`,
> `sshTarget`, `daemonCommand`, `DaemonConnection`, `roomSourceReader`), what
> stays job-only, and its name?

Three sub-questions. This document answers all three, and argues that the third
should be answered *first* — by creating a tier, not by naming a file.

## 1. Answer the third question first: create the tier

Today `src/` is 26 modules for two programs with no directory saying which
module serves which program (RV-001 F-1). Twelve are the runner's contract by
convention only: `json`, `fields`, `context`, `project-context`, `config`
(`parseModel` alone), `session` (`registryOf` alone), `grep`, `message-of`,
`models`, `ndjson`, `truncate`, `unix-socket`.

satan:SL-027 wants to move code in the **opposite direction** — out of `src/runner/`
and into shared use. If the only home for shared code is `src/` root, the room
module lands there by default and the ambiguity F-1 named gets worse, not
better: after satan:SL-027 there would be shared room mechanism, with two clients,
sitting beside daemon-private modules, with nothing to distinguish them.

So the tier is the precondition. Two directories, named for what they are, not
one bucket called `shared`:

- **`src/lib/`** — pure leaves with no notion of a program: `json`, `fields`,
  `message-of`, `truncate`, `xml`, `ndjson`, `unix-socket`, `context`, `models`,
  and `parseModel`/`ModelRef`/`DEFAULT_MODEL` out of `config.ts`.
- **`src/room/`** — the room session: the pi-env connection, its launch, its
  shell, its `SourceReader`, and the connection facts. That is `inq-2`'s
  module, and this is its name.

With those two, `inq-2`'s "what moves out" has an answer that is structural
rather than a judgement call, and "its name" is answered by the destination.

### Two-sided, not one-sided

RV-001 F-1 recommended a structural test in the pattern of
`test/runner/room.test.ts` "door knowledge (EX-10)" — an allowlist asserted
over source text. satan:SL-027 changes what the test must say. The one-way arrow
("only `runner-main.ts` imports `runner/*`") is real today and satan:SL-027 retires
it. The rule to assert is:

- no module outside `src/runner/` imports `src/runner/*`;
- no module in `src/runner/` imports daemon-private modules (`daemon*`,
  `session`, `protocol`, `render`, `attach*`, `persona`, `skills`, `cwd`,
  `satan-tools`, `config`'s `Config`/`resolveConfig`);
- both programs may import `src/lib/*` and `src/room/*`.

Assert the allowlist explicitly, file by file, as EX-10 does — a wildcard
allowlist stops being a boundary. This test is also the cheapest proof of
satan:SL-027's own closure criteria ("the shared env module covered once; the runner's
suite green unchanged").

## 2. What moves out, and what stays job-only

The cut should be made by **consumer**, not by line span and not by file. The
discriminator: *would the daemon need this to have a room session?* If yes it
moves; if it exists because a job is a reviewable unit of work, it stays.

### Moves to `src/room/` (shared)

| symbol | today | why shared |
|---|---|---|
| `RoomConnection`, `Launch` | `room.ts:492-521` | the facts a pi-env connection is built from; two clients, one room |
| `daemonLaunch`, `roomConnection` | `room.ts:516-533` | derive those facts from config; the daemon needs both (see §3 on their config dependency) |
| `sshTarget`, `DaemonHelpers`, `daemonCommand`, `DaemonConnection`, `daemonConnection` | `env.ts:152-253` | already generic; `env.ts`'s own header (EX-3/EX-4) says they must not know which kind of room or which client |
| `HostKeyFailure`, `LostFailure`, `ConnectionObserver` | `env.ts:31-41` | observation shapes; the *reaction* is per client, the shape is not |
| `RoomShell`, `ShellLimits`, `ShellOutput` | `room.ts:70-104` | the daemon's **startup** project-context read happens outside any conversation, so it needs bounded exec with no conversation in hand |
| `notOverflowed`, `succeeded` | `room.ts:145-168` | generic exec result helpers over `RoomShell` |
| `outputCollector`, `settle`, `roomShell`, `OVERFLOW_EXIT_CODE` | `shell.ts` (whole file) | the standalone exec path; the daemon has no conversation to borrow one from at startup |
| `ChannelUnavailable`, `ChannelFailed` | `room.ts:108-140` | the error taxonomy is shared; **the reaction is not** — see §4 |
| `roomSourceReader` + `FETCH_LIMITS`, `HEAD_LIMITS`, `DOCTRINE_LIMITS` | `runner/project-context.ts:156-203, 25-45` | a `SourceReader` adapter over the room shell; satan:DEC-072 wants the daemon's context read in the environment too. "Promote, don't duplicate" |
| `HostKeyChangedError`/`HostKeyUnknownError` re-exports | `env.ts:171-174` | so neither client imports pi-env for the trust test |

`roomSourceReader` will not promote cleanly as it stands: it is entangled with
job admission — `Degradation`, `PrepareFailed`, `FinalStep` (job-only, below).
Splitting adapter from admission is part of the work, not an afterthought.

### Stays job-only (in `src/runner/`)

| symbol | today | why it stays |
|---|---|---|
| `GitChannel` (refresh/collect/reachable) | `room.ts:28-62` | it exists to bring commits to a **quarantine for human review**; the daemon has no quarantine, no promotion, no receipt |
| `CapsuleCli`, `execCapsule`, `provisionArgs`, `collectArgs`, `probeArgs`, `returnToWorkArgs`, `roomPushArgs`, `roomCollectArgs`, `roomVerbError`, `slotChannel`, `roomChannel`, `collectedJobRef` | `room.ts:172-460` | the git-transfer mechanism and its two adapters |
| **the slot door entirely** | `room.ts:198-296` | the daemon reaches a room, never a slot. There should be no daemon adapter for it, and `[door] kind` selection stays the runner's |
| `checkRoomClone`, `cleanRoomClone`, `CloneDefect`, `PREPARE_LIMITS` | `room.ts:70-75, 434-471` | clone hygiene is *job admission*: refuse a dirty `/work` clone, clean after collect. The daemon owns `/home/agent` and no clone (D3) |
| `jobBranch` | `room.ts:172` | a job's branch name |
| `RepoReader`, `gitRepoReader` | `git.ts` | I3 is the **runner's** invariant (reads the real repo only to resolve a base). The daemon reads no real repo |
| `JobConnection`, `jobEnv`, `ConnectionObserver`'s pause use, `pausingObserver` | `env.ts`, `pause.ts` | these are the room-down **pause**; the daemon has no pause (it has `inq-5` instead) |
| `Degradation`, `PrepareFailed`, `FinalStep`, `readyRoom` | `prepare.ts`, `runner/project-context.ts` | job admission and its audit vocabulary |

Note what this table implies about the existing file: **`src/runner/room.ts`
holds both halves and is misnamed for it.** Its header says "the git channel …
this file and `config.ts` are the only ones that know the door", which is
accurate — but the door (transfer, door kind, slot) is the job's, while the
room session is shared. After this move, "room" should mean the session.
Rename the remainder to what it is (`runner/door.ts`, or `runner/channel.ts`)
in the same change. Do it while the file is being split anyway; F-1's cost is
at its lowest exactly here.

## 3. The config dependency inq-3 will hit

`roomConnection(config)` and `daemonLaunch(config, repo)` read **`RunnerConfig`**
(`runner/config.ts:395-454`: `DoorConfig`, `SlotDoorConfig`, `RoomDoorConfig`,
`doorOf`). Moving them to `src/room/` therefore drags `[door]`-shaped config out
of `runner/`, which is `inq-3` ("Daemon door and room cwd configuration: shape
(HA `[door]` keys?), source (env, file, HM-rendered ssh_config), NF-006
naming"). Two consequences:

- The room facts need a **client-neutral shape** (`RoomConnection` already is
  one) and a way to be built from either program's configuration. Whether the
  daemon reuses `[door]` keys, or gets an env-based resolver that produces the
  same shape, is `inq-3`'s call — but the *shape* belongs to `src/room/`, and
  the *parsing* stays with each program's config.
- The two `config.ts` modules are already a find (RV-001 F-4): `src/config.ts`
  resolves the daemon's environment to paths, `src/runner/config.ts` parses
  TOML; they share a name and duplicate `Env` and "required and non-empty".
  satan:SL-027 makes this an interface seam rather than a tidiness item. Split
  `src/config.ts` (`parseModel` → `src/lib/`, `Config` → daemon) and put the
  door *types* in `src/room/` while the door *parsers* stay per program.

## 4. The invariants that must travel, and one that must not

The extraction is safe only if three rules survive it. They exist today as
comments carrying foreign labels (RV-001 F-2):

- **EX-3/EX-4 — the connection is built from facts, never from a kind.**
  `env.ts` "never knows which kind of room it reaches"; `roomConnection` and
  `daemonLaunch` are the only sources of connection facts. One level up, the
  same rule is the test for this whole RFC: **the room module must not know
  which client it serves.** If a shared function needs to ask "job or daemon?",
  it belongs to neither — split it, or inject the difference.
- **EX-5 — a host-key failure is a trust failure, never downtime.** The runner
  trips a latch (`host_key`) and collects; the daemon must not treat it as a
  transient room outage to retry (`inq-5`). The type and the record
  (`DaemonConnection.trustFailure`) are shared; the policy is not.
- **I3 — the real repo is read only to resolve a base.** Shared code must not
  acquire repo-reading habits as it moves; `RepoReader` stays behind.

And the rule that must **not** travel: **the pause.** The runner's room-down
handling is `pause_requested` on a job row, the guard's `afterTool`/`afterTools`
hooks, and a resume message (satan:DEC-055). None of that is a room fact; it is job
lifecycle. `pausingObserver` and `JobConnection`'s observer wiring stay in
`runner/`. A shared module that starts offering "what to do when the room is
lost" will accrete both clients' policies and become a union of flags — the
degeneration risk below.

Do **not** let the profile (satan:CON-005) into the module. satan:SL-027 objective 6 and
tension T1 settle it: the launcher selects the profile, the daemon builds the
environment its jail permits. The room module takes facts and builds a session;
it must stay profile-agnostic, or `egress`/`host` will arrive as branches
inside it.

## 5. Ordering, and the one thing not to bundle

1. `src/lib/` + `src/room/` exist, with the two-sided structural test. Small,
   mechanical, and it makes the rest a move rather than a judgement.
2. The room module lands in `src/room/` per §2, invariants stated in its own
   header at the point of difficulty (§4).
3. `runner/door.ts` rename, with the split, in the same change.
4. Then `inq-3` (door config for the daemon) and `inq-7` (project context
   through the room) — both become *uses* of the module rather than further
   boundary questions.
5. **Do not bundle `run.ts`.** RV-001 F-3: 660 lines, seven concerns, no
   harness-free test. It is adjacent (it is where admission meets the room) but
   orthogonal: nothing in satan:SL-027's dependency graph touches the job lifecycle.
   Its re-cut needs "where does admission belong", which is the very boundary
   satan:SL-027 is now deciding; cutting it before guesses, cutting it during makes
   the slice carry two designs. It stays IMP-002 step 4, after satan:SL-027.

One ordering caution that is not in §2 but outranks it: **the live two-client
probe belongs before the boundary is locked, not at `inq-10`.** satan:SL-027's risk
Q2 ("does pi-env tolerate two concurrent connections; does the runner assume it
owns the room?") determines whether "shared room session" is a true abstraction
or two thin adapters over pi-env's primitives. The research is reassuring
(each `Connection` spawns its own `ssh … serve --token`; the runner assumes
exclusivity only of `/work/<repo>`), but the daemon-side Rust locking is
unread. If that probe fails, §1's tier still stands and §2's cut mostly stands,
but the module's shape changes from "a session both clients hold" to "the
primitives both clients build a session from" — worth knowing before the design
locks.

## Risks and how this advice fails

- **Degeneration.** The likely failure of any shared module here is a boundary
  that accretes both clients' policies (pause, profile, retry, tool-error
  mapping). The guardrail is §4's EX-4 test, applied per function: *does it ask
  which client it serves?* If yes, it is in the wrong place. The first
  candidate for erosion is visible already: `grep.ts` is shared today, and the
  daemon's room outage currently surfaces through it as "ripgrep (rg) is not
  available" (`grep.ts:363-365`, `inq-5`). Do not fix that by teaching the
  shared tool about profiles — inject the error mapping.
- **Naming debt mistaken for design.** If the move keeps the word "room" for
  both the session and the transfer, every future mention needs a
  disambiguation and the tier's name stops doing work.
- **False precision.** The inventory in §2 is drawn from the code as it stands
  on 2026-10-19. It is a starting map, not a specification; satan:SL-027's own line
  ranges (research §Thread 2) are the authority on where the seam currently
  falls.
- **The slice is not the place for the whole tier.** satan:SL-027 needs `src/room/`
  to exist, not `src/lib/` to be perfect. If the daemon half of the slice is
  under time pressure, step 1 can be reduced to `src/room/` plus a test that
  permits exactly today's edges and forbids new ones — leaving `src/lib/` to
  IMP-002.

## Open questions this RFC does not answer

- `inq-3`: whether the daemon reuses `[door]` keys or gets an env resolver, and
  how NF-006 naming applies. §3 constrains the shape, not the source.
- `inq-5`: the daemon's per-call room-down behaviour and grep's error mapping.
  §4 says the taxonomy is shared and the policy is not; the policy is `inq-5`'s.
- `inq-7`: the daemon half of satan:DEC-072 (`gitRootDirs` uses host `existsSync`,
  `src/project-context.ts:121-134`). §2 shares the reader; the root walk is a
  separate question.
- The module's public surface: whether it exposes a `Connection` factory, a
  `Session` object, or both. This RFC argues only for its contents and its
  independence; the shape is a design decision for satan:SL-027.
